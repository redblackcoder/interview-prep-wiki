# Design a Web Crawler (Scaling-Focused) — Self-Interview + Graded Review

A re-attempt of the 2026-05-11 Atlassian web-crawler screen ([[sources/docs/web-crawler-system-design]]), this time **deliberately skipping the API/job-interface layer** to spend the whole round on the crawl-scaling crux: how one worker sustains ~1k docs/s on I/O-bound work, and how the fleet dedups + stays resilient at 10k–100k docs/s. Graded here against the same rubric as every other round — the **Competency matrix** in [[private/staff-swe-readiness-report]] — and compared directly to the #1 baseline to measure growth. Transcript: [self-web-crawler-scaling-design/](https://github.com/redblackcoder/interview-prep-raw/blob/master/docs/self-web-crawler-scaling-design/Transcript.md).

**Verdict: lean hire, ~7/10 at the Staff bar. Promising, not yet principal-clean.** The crux was entered and driven to real depth (the async-I/O throughput argument and the connection-reuse insight are genuinely strong), but two familiar seams recurred — a dual-write ordering bug on the resilience path and an 8× byte/bit slip in the bandwidth math — and the domain-hard part (politeness + recrawl scheduling) was scoped out up front rather than closed.

## Key Ideas (and where the design is right vs. must close)

- **K0 — The crux is I/O-bound throughput, and the async argument is correct.** The pivotal move: "10k docs/s ≠ 10k machines, because a fetcher is almost never on-CPU — it's parked on network I/O." Hand the socket to the kernel, let an **event loop** drive thousands of in-flight fetches, and offload the CPU-bound parse to a **separate thread pool** so it never blocks the loop. This is the right mental model and is driven to real depth. It's the single clearest piece of evidence that **G3 (comfort-zone drift) did not recur** — the unfamiliar crux was entered and stayed in.
- **K0b — Connection reuse falls out of host co-location, not connection count.** The sharpest insight in the round: "1k docs/s does *not* mean 1k open sockets." If work is partitioned so one worker owns a set of **hosts**, its fetches concentrate on few servers → the kernel **reuses TCP connections**, and **HTTP/2 multiplexes** many requests per connection (no repeated handshake). Correctly names HTTP/2 **head-of-line blocking** (one slow response stalls the shared connection) and reaches for **QUIC/HTTP-3** (independent streams, no transport-level HOL) as the fix. This is at-or-above bar.
- **K1 — The dual-write seam (correctness gap, highest priority).** The design says "put the new URLs in the Redis seen-set, *then* push them to the Kafka queue." That ordering **loses work on crash**: mark-seen succeeds, worker dies before enqueue → the URL is now permanently deduped-away but never queued → **silently never crawled.** This is the same *detection ≠ closure* seam the report tracks as **G2**. Fix: **reverse the order** — enqueue first, then mark seen — and only **commit the Kafka input offset after** both the content is durably stored *and* the child URLs are enqueued. At-least-once + idempotent dedup then makes a crash replay safe (worst case: re-fetch, not lose). The design named "don't lose work on crash" as a top goal and then built the one ordering that loses it — closing this is the difference between lean-hire and strong-hire.
- **K2 — "Batch SADD is atomic" hides a membership gap and a cross-slot problem.** Two issues under the claim that Redis serializes concurrent workers cleanly: (1) A single `SADD key m1 m2 m3` is atomic, but it returns only a *count* of new elements, not *which* were new — so you can't tell which URLs to enqueue. You need **per-URL novelty** (did *this* URL transition unseen→seen?). (2) In a **sharded** Redis, the members of one batch hash to **different slots/shards**, so there is no single atomic multi-key op across them. Fix: **N per-key check-and-adds** (`SADD key one-url`, or a small Lua script), pipelined; each returns 0/1, and **1 = novel = the enqueue signal**. This makes K1's ordering per-URL exact.
- **K3 — The authoritative seen-set doesn't fit in RAM at web scale.** Billions of URLs × tens of bytes ≫ economical Redis memory (multi-TB). The scaling answer is the classic two-tier: a **Bloom filter** (or per-shard RocksDB/SSD-backed set) as the cheap in-front membership check, backed by an authoritative on-disk set; Redis holds only hot/recent keys. The design used Redis as the whole seen-set — fine for the interview's stated scope, but the web-scale version must name the memory wall. (This is exactly what the #1 design's Bloom-filter box was for — the two designs together imply the right layered structure.)
- **K4 — Partitioning incoherence (the one real architecture flaw).** The design shards **Redis/dedup by URL**, but the throughput argument (K0b) needs **host co-location** for connection reuse — and politeness needs it too. Two different partition keys pulling against each other. **Unify on host**: partition the frontier, the dedup, *and* the fetch assignment all by **host** (via [[wiki/theory/consistent-hashing]]). Then connection reuse, DNS-cache locality, **and** per-host politeness/rate-limiting all fall out **for free** from the same decision — one partition key buys three properties. This is the insight that ties the whole design together and it was left implicit.
- **K5 — The 8× byte/bit slip (G1, recurred to type).** "1000 docs/s × 10 KB = 10 Mbps." That's **bytes vs bits**: 1000 × 10 KB = 10 **MB**/s = **80 Mbps**, not 10. The rack rollup ("50 servers → 500 Mbps") is really ~**4 Gbps**. **Non-fatal** — the conclusion (well under a 10–25 Gbps NIC) still holds — but it's the same unit-slip family (÷/× by a power the report flags under **G1**). The fix is the drilled reflex: **carry units explicitly** (KB→Kb is ×8) and sanity-check the magnitude.
- **K6 — Kafka is a log, not a drainable delay-queue; recrawl needs a scheduler.** The tiered-topic idea (real-time / daily / weekly topics) conflates two things: **priority classes** (legit — separate topics/consumer pools so a slow bulk tier can't starve real-time) and **time-delayed scheduling** (not what a log does — you can't "crawl this again next Tuesday" by parking it in a Kafka partition). Recrawl wants a **scheduler**: a **Redis sorted set / DB keyed by `next_crawl_time`**, a due-poller that enqueues when a URL comes due, and cadence set by observed change-rate. Pair with **conditional GET** (`ETag` / `If-Modified-Since`) and a **content hash** to skip unchanged pages cheaply. This was correctly flagged as a requirement but the mechanism was left at "tiered topics."
- **K7 — Minor: the BFS justification is a non-sequitur.** "We must download a page before we can see its links, therefore BFS." True premise (fetch-before-expand), but it argues for neither BFS *nor* DFS — both expand only discovered frontier nodes. The real reason to prefer **BFS** is **politeness and freshness**: breadth spreads load across hosts and reaches high-value shallow pages first, whereas DFS tunnels deep into one host (rude, and starves breadth). Right answer, wrong reason — worth getting the *why* clean.

## Growth vs. #1 (what changed since the Atlassian screen)

- **G3 (comfort-zone drift) — did NOT recur, and this is the headline.** #1 "stayed at the API/job-interface layer; the genuinely hard parts were left as open questions." This round did the opposite: **skipped the comfortable API layer on purpose** and spent the whole time *inside* the crux (async I/O, connection reuse, HOL/QUIC, dedup coordination). This is the second consecutive round (after [[sources/docs/design-instagram-auction-mock-interview]]) where drift didn't fire — still "coachable, not yet automatic," but now with a crawler data point on the *same problem* that previously triggered it. Real, measurable growth on the report's hardest-to-move axis.
- **G2 (detection ≠ closure) — recurred, same shape.** The dual-write ordering seam (K1) and the SADD-novelty gap (K2) are textbook last-hop misses: the design *names* "don't lose work on crash" and then doesn't close the mechanism that guarantees it. Identical in spirit to the ChatGPT token-return path and the Uber atomic-claim seam. The last mile from lean-hire to strong-hire is still this reflex.
- **G1 (estimation) — recurred, non-fatally.** The 8× byte/bit slip (K5). Milder than the ChatGPT/Uber 10× *arithmetic* slips because the fleet-sizing logic was sound and the conclusion survived — but it's the same unit-discipline gap, and it confirms G1 is "not yet the floor."
- **G4 (dropped threads) — improved in form.** #1 *raised* politeness/worker-death and then *parked* them. This round **scoped politeness/robots out up front with a reason** ("if we have time at the end") — a more honest move than raise-then-drop — but the domain-crux (per-host politeness across a fleet + recrawl scheduling, K6) still went un-designed. Better discipline, same residual gap.
- **Net:** consistent with the report's one-line verdict — *ceiling rising and real; floor + last-hop closure remain the gate.* The crawler, historically the drift exemplar, is now a crux-entered round. One self-graded round doesn't raise the floor, so the report's "Now" column is unchanged; this is logged as corroborating evidence, not a promotion.

## My Understanding

- The thing I'm genuinely proud of: I found the **real** reason the naive "one thread per fetch, so 10k machines" estimate is wrong, and I didn't stop at "use async" — I chased it into *why the connection count stays low* (host co-location → TCP reuse → HTTP/2 multiplexing), and I knew the next failure (HTTP/2 HOL) and its fix (QUIC). That's the crux, entered and driven, on the exact problem type that used to make me retreat.
- My real miss is the same one the report keeps flagging: I **named crash-safety as a goal and then built the ordering that violates it.** Marking a URL seen *before* it's safely enqueued means a mid-crash silently drops it from the crawl forever. The fix (enqueue-then-mark; commit the source offset only after store + enqueue; per-URL novelty from the SADD) was fully within reach — I just didn't run the "what does a crash between these two writes do?" check. That check is the last mile.
- I also let two partition keys fight: dedup-by-URL vs. the host-co-location my own throughput argument depended on. Unifying on **host** would have bought connection reuse, DNS locality, *and* politeness from one decision — I had all the pieces and didn't connect them.
- The bandwidth number was right in spirit and wrong by 8× (bytes vs bits). It didn't change the conclusion, but it's the unit-carrying discipline I keep saying I'll make free.

## Interview-Craft Lessons

- **Run the crash-in-between check on every pair of writes.** Any time two stores must both happen (mark-seen + enqueue; store-content + commit-offset), narrate "what if the process dies between them?" and order them so the *recoverable* failure (re-do work) is the only one possible — never the *unrecoverable* one (lose work). This is the crawler instance of the report's **seam reflex**.
- **When a batch op returns a count, ask what you actually needed — the count or the identities.** `SADD`'s new-element *count* isn't the *which*. If downstream action depends on per-item novelty, you need per-item ops. Same for any "atomic batch" that spans shards — atomicity is per-key, not per-batch.
- **Make the partition key earn multiple properties before you pick it.** Before committing a shard key, list everything that wants locality (dedup, connection reuse, politeness, storage) and pick the key that serves the most. Host does; URL doesn't.
- **Carry units through every estimate.** KB vs Kb is ×8; the reflex is to write the unit next to the number and sanity-check the order of magnitude, not just the digits.
- **Separate priority from scheduling.** "Some things are more urgent" → priority classes (separate queues/pools). "Crawl this again later" → a time-indexed scheduler (`next_crawl_time` sorted set), not a parked log message. Don't let one mechanism pretend to be both.
- **Scoping-out is stronger than raising-then-parking.** "I'll skip robots.txt with a reason and come back if there's time" beats flagging politeness and leaving it in an Open-Questions bin — but only if you actually reserve time to close the domain-crux, or it's the same G4 miss in nicer clothes.

## Open Questions

- **Per-host politeness across a distributed fleet:** with host-based partitioning, per-host `crawl-delay` is a *local* token bucket at the owning worker — but how does rebalancing (a host moving shards) hand off the rate-limit state without a burst that violates politeness during the transition?
- **Frontier prioritization:** beyond recrawl cadence, how are *new* URLs prioritized (page importance / PageRank-ish, depth, freshness) so the real-time tier isn't just FIFO? Where does the priority score live and who computes it?
- **The authoritative seen-set at web scale:** concretely, Bloom-in-front-of-RocksDB per host-shard vs. a shared store — what's the false-positive budget (a Bloom FP means a real page is *never* crawled), and how is the filter rebuilt/scaled as the corpus grows?
- **Recrawl mechanism end-to-end:** sorted-set-by-`next_crawl_time` + due-poller + conditional GET (`ETag`/`If-Modified-Since`) + content-hash-to-skip — how do these compose, and how is cadence adapted from observed change-rate per URL?
- **Exactly-once-ish storage:** if a worker stores content to S3, then crashes before committing the Kafka offset, replay re-fetches and re-stores — is the object keyed by URL (idempotent overwrite) or is there a dedup on content hash to avoid duplicate objects?
