Istio + Envoy + RLS: a deployment you can read

Two services (one public, one internal) plus a global rate-limit service — the complete Kubernetes + Istio manifests, and how every file maps to what actually runs.
KubernetesIstioEnvoy envoyproxy/ratelimitRedismTLS

0 · What we're building

  • Service A — an HTTP app exposed to the outside world through an Istio ingress gateway.
  • Service B — an internal-only HTTP app. No external door; only Service A may call it.
  • Service A calls Service B on every request it receives.
  • RLS — the envoyproxy/ratelimit global rate-limit service (this repo), backed by Redis, wired to the ingress gateway so external traffic to Service A is rate-limited.
The one idea to hold onto
You never write "an Envoy config" or "a proxy" by hand. You write Kubernetes objects (Deployments, Services) and Istio custom resources (Gateway, VirtualService, EnvoyFilter…). A control-plane component called istiod watches all of those and compiles them into Envoy configuration, which it pushes to every proxy. Your YAML is the source; the running Envoys are the output. Every file below is you editing that source.

2 · The six building blocks (plain-English)

ThingWhat it isYou write it?
PodThe smallest runnable unit — one or more containers sharing a network address. Your app runs here.No — created for you by a Deployment
Deployment"Keep N copies of this pod running." Manages rollout/scaling. You describe the pod once; it makes the copies.Yes
ServiceA stable name + virtual IP in front of a set of pods. service-b resolves to whatever B-pods currently exist. This is how A finds B.Yes
Sidecar (Envoy)A proxy container Istio injects next to your app. All the pod's traffic goes through it — that's where mTLS, routing, and rate-limit checks happen. Your app is unaware of it.No — auto-injected
Istio CRDsGateway, VirtualService, PeerAuthentication, AuthorizationPolicy, EnvoyFilter — declarative rules istiod turns into Envoy config. They configure proxies; they don't run.Yes
istiodThe control plane. Watches your CRDs + the cluster state, compiles Envoy config, pushes it to every sidecar & gateway, and issues each workload its mTLS identity certificate.No — installed once
Deployment → ReplicaSet → Pod → (app + sidecar)
You write a Deployment whose template has one container (your app). Because the namespace is labelled for injection, the pod that actually starts has two containers: your app and the istio-proxy sidecar. You never see the sidecar in your YAML — that's the point.

00-namespace.yamlKubernetes
apiVersion: v1
kind: Namespace
metadata:
  name: demo
  labels:
    istio-injection: enabled   # every pod created in "demo" gets an Envoy sidecar auto-injected

One label does a lot: it tells istiod to inject the sidecar into every pod in this namespace. Without it, your pods run bare and none of the Istio features (mTLS, routing, rate limiting) apply.

01-service-b.yamlthe internal service
# A ServiceAccount is the workload's IDENTITY. Istio mints an mTLS cert for it:
#   spiffe://cluster.local/ns/demo/sa/service-b
apiVersion: v1
kind: ServiceAccount
metadata:
  name: service-b
  namespace: demo
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: service-b
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: service-b
  template:
    metadata:
      labels:
        app: service-b        # <- sidecar injected (namespace label); pod runs app + istio-proxy
    spec:
      serviceAccountName: service-b
      containers:
        - name: app
          image: hashicorp/http-echo:1.0    # stand-in for your real app
          args: ["-listen=:8080", "-text=hello from service-b"]
          ports:
            - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: service-b
  namespace: demo
spec:
  selector:
    app: service-b            # this Service fronts every pod labelled app=service-b
  ports:
    - name: http              # NAME matters: Istio detects L7 protocol from the "http" prefix
      port: 8080
      targetPort: 8080
  # No type => ClusterIP => reachable ONLY inside the cluster. This is what "internal" means, part 1.
How "internal only" is achieved (part 1 of 2)
A plain ClusterIP Service has no external address — nothing outside the cluster can reach it. B becomes internal simply by never being pointed at by a Gateway. Part 2 (file 05) adds identity-based authorization so even inside the cluster only A may call it.

Service A is an nginx that forwards each request to service-b. The important line is proxy_pass … service-b…:8080 — A reaches B by its Service DNS name, and the sidecars transparently upgrade that call to mTLS. A's app code knows nothing about certificates.

03-gateway.yamlexpose A to the world
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: demo-gateway
  namespace: demo
spec:
  selector:
    istio: ingressgateway     # binds these rules to the shared istio-ingressgateway Envoy (in istio-system)
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "*"                  # accept any Host header (fine for a demo)
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: service-a
  namespace: demo
spec:
  hosts:
    - "*"
  gateways:
    - demo-gateway            # apply this routing to traffic that entered via demo-gateway
  http:
    - match:
        - uri:
            prefix: /
      route:
        - destination:
            host: service-a.demo.svc.cluster.local    # send it to Service A
            port:
              number: 8080
Gateway vs VirtualService — the split that confuses everyone
Gateway = "open this port/protocol/host at the edge" (the door). VirtualService = "once traffic is inside, route path X to service Y" (the signposting). The istio-ingressgateway itself is a pre-existing Envoy deployment installed with Istio; the selector: istio: ingressgateway is what attaches your door to it. Neither of these is a running server you deploy — they're config for one that already exists.
04-mtls.yamlsecurity
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: demo
spec:
  mtls:
    mode: STRICT      # every pod-to-pod call between sidecars in "demo" must be mutually-TLS authenticated

This makes the mesh encrypt and mutually-authenticate all in-mesh traffic. It's what gives file 05 something to check: once mTLS is on, every call carries a verified caller identity (the SPIFFE name from the caller's ServiceAccount).

05-authz-service-b.yamlinternal-only, part 2
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: service-b-allow-only-a
  namespace: demo
spec:
  selector:
    matchLabels:
      app: service-b          # this policy is enforced by B's own sidecar
  action: ALLOW
  rules:
    - from:
        - source:
            principals:
              - "cluster.local/ns/demo/sa/service-a"   # ONLY Service A's mTLS identity is allowed
This is the identity story made concrete
B's sidecar checks the verified mTLS principal of the caller against this allow-list. Anything that isn't Service A — another pod, a curl from a debug container — is rejected with 403, inside the cluster. This is exactly the "verified service identity, not IP" idea: the key is A's ServiceAccount, which can't be spoofed because it's backed by a certificate istiod issued.

The config.yaml here is exactly the descriptor tree parsed by src/config/config_impl.go; the env vars map to src/settings/settings.go; and each request drives the INCRBY+EXPIRE in src/redis/fixed_cache_impl.go. The Deployment is "ordinary workload" — nothing Istio-specific about the RLS itself.
08-envoyfilter-ratelimit.yamlwire the filter

Istio has no built-in "global rate limit" CRD, so you reach for the escape hatch — EnvoyFilter — to patch two things into the ingress gateway's Envoy: (a) the rate-limit HTTP filter, and (b) a cluster telling it how to reach the RLS.

apiVersion: networking.istio.io/v1alpha3      # EnvoyFilter only exists in v1alpha3
kind: EnvoyFilter
metadata:
  name: ratelimit-filter
  namespace: istio-system                     # patch the shared ingress gateway
spec:
  workloadSelector:
    labels:
      istio: ingressgateway
  configPatches:
    # (a) insert the global rate-limit filter into the gateway's HTTP filter chain
    - applyTo: HTTP_FILTER
      match:
        context: GATEWAY
        listener:
          filterChain:
            filter:
              name: envoy.filters.network.http_connection_manager
              subFilter:
                name: envoy.filters.http.router
      patch:
        operation: INSERT_BEFORE
        value:
          name: envoy.filters.http.ratelimit
          typed_config:
            "@type": type.googleapis.com/envoy.extensions.filters.http.ratelimit.v3.RateLimit
            domain: ratelimit                 # <- MUST equal the ConfigMap domain in file 07
            failure_mode_deny: false           # fail-open if the RLS is unreachable
            timeout: 0.1s
            rate_limit_service:
              transport_api_version: V3
              grpc_service:
                envoy_grpc:
                  cluster_name: rate_limit_cluster
    # (b) define that cluster: a plain gRPC/HTTP2 target pointing at the RLS Service
    - applyTo: CLUSTER
      match:
        cluster:
          service: ratelimit.demo.svc.cluster.local
      patch:
        operation: ADD
        value:
          name: rate_limit_cluster
          type: STRICT_DNS
          connect_timeout: 1s
          lb_policy: ROUND_ROBIN
          http2_protocol_options: {}          # gRPC requires HTTP/2
          load_assignment:
            cluster_name: rate_limit_cluster
            endpoints:
              - lb_endpoints:
                  - endpoint:
                      address:
                        socket_address:
                          address: ratelimit.demo.svc.cluster.local
                          port_value: 8081
09-envoyfilter-actions.yamlwhat to count

File 08 turned the feature on; this file says what identity to send. It adds a rate-limit "action" to the gateway's route — a descriptor generator (from the study guide's §5.2a).

apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: ratelimit-actions
  namespace: istio-system
spec:
  workloadSelector:
    labels:
      istio: ingressgateway
  configPatches:
    - applyTo: VIRTUAL_HOST
      match:
        context: GATEWAY
      patch:
        operation: MERGE
        value:
          rate_limits:
            - actions:
                - generic_key:
                    descriptor_value: service_a_ingress   # emits (generic_key, service_a_ingress)
The two halves must agree
The action here emits the descriptor (generic_key, service_a_ingress). The RLS config in file 07 has a matching entry key: generic_key / value: service_a_ingress. The gateway builds the descriptor; the RLS looks it up. If these don't match, the RLS finds no limit and everything passes (fails open, silently) — see gotcha #2. To rate-limit per client instead of globally, you'd swap generic_key for a remote_address or request_headers action (§5.2a of the study guide).

4 · Who configures what (the mental map)

The thing that finally makes it click: almost every file is really just configuring one or more Envoys. Here's the mapping.

Your fileWhat istiod turns it intoWhich Envoy it lands on

Service (any)an Envoy cluster (a named upstream) + endpointsevery proxy
Gatewaya listener on port 80ingress gateway
VirtualServiceroute rules (path → cluster)ingress gateway (+ sidecars)

AuthorizationPolicy (B)an RBAC filter allow-ruleB's sidecar

The RLS ConfigMap is the one exception — it isn't Envoy config at all; it's the RLS's own application config, loaded by the RLS process independently (a nice reminder that the RLS is a normal service with its own config lifecycle, not an Istio object).

5 · One request, end-to-end

  1. External client hits the cloud load balancer → the istio-ingressgateway Envoy on port 80.
  2. The gateway matches the request to your Gateway's listener, then the VirtualService route (prefix / → Service A).
  3. Before routing, the rate-limit HTTP filter (file 08) fires. It builds the descriptor (generic_key, service_a_ingress) from the action (file 09) and makes a gRPC ShouldRateLimit call to rate_limit_cluster → the RLS.
  4. The RLS looks up the descriptor in its config (domain ratelimit), does INCRBY+EXPIRE in Redis, and returns OK or OVER_LIMIT.
  5. OVER_LIMIT → the gateway returns 429 immediately; Service A is never touched. OK → routing proceeds.
  6. The gateway forwards to Service A's pod. Its sidecar receives the mTLS connection, hands plaintext to the nginx app.
  7. Service A calls service-b:8080. A's sidecar opens an mTLS connection to B's sidecar, presenting A's SPIFFE identity.
  8. B's sidecar checks the AuthorizationPolicy (file 05): caller principal is …/sa/service-a → allowed. It hands the request to B's app.
  9. B responds → back through both sidecars → Service A → gateway → client.

The 11th request within a minute takes the same path until step 4, where Redis returns 11 > 10 → step 5 short-circuits with a 429.

6 · First-timer gotchas

#1 · domain mismatch = silent no-op
The domain in the HTTP filter (file 08) must equal the domain in the RLS ConfigMap (file 07). If they differ, the RLS has no config for what it's asked and returns OK for everything. No error, no limit. This is the single most common "why isn't it working?"
#2 · descriptor mismatch = also silent
The action in file 09 and the descriptor entry in file 07 must line up key-for-key and value-for-value. A typo means "no matching limit" → pass. Rate limiting fails open, so mistakes hide.
#3 · RUNTIME_IGNOREDOTFILES=true
Kubernetes mounts a ConfigMap using hidden ..data symlink directories. Without this env var the RLS tries to parse them as config and errors. Always set it when the config comes from a ConfigMap.
#4 · keep RLS & Redis out of the mesh (here)
The custom rate_limit_cluster (file 08) dials the RLS as plain HTTP/2. If the RLS had a sidecar with STRICT mTLS, that plaintext call would be rejected. The simple fix in this demo is sidecar.istio.io/inject: "false" on RLS and Redis. (A production alternative: inject them and reference Istio's auto-generated outbound|8081||ratelimit.demo.svc.cluster.local cluster instead of hand-rolling one, so mTLS is handled for you.)
#5 · EnvoyFilter is a sharp tool
It patches raw Envoy config and can break a proxy if the match doesn't hit. It lives only at networking.istio.io/v1alpha3, and here it targets the shared gateway in istio-system — a mistake there affects all gateway traffic. Use it only where Istio has no higher-level API (global rate limiting is one such case).
#6 · port names are semantic
Istio infers L7 protocol from the Service port name (http, grpc, tcp-redis…). Name an HTTP port foo and Istio treats it as opaque TCP — routing and rate limiting won't apply.

7 · Apply & test it

Assuming a cluster with Istio installed (istioctl install --set profile=demo -y gives you istiod + the ingress gateway):

kubectl apply -f 00-namespace.yaml
kubectl apply -f 01-service-b.yaml -f 02-service-a.yaml
kubectl apply -f 03-gateway.yaml -f 04-mtls.yaml -f 05-authz-service-b.yaml
kubectl apply -f 06-redis.yaml -f 07-ratelimit.yaml
kubectl apply -f 08-envoyfilter-ratelimit.yaml -f 09-envoyfilter-actions.yaml

# find the gateway's external address
kubectl -n istio-system get svc istio-ingressgateway
GW=<EXTERNAL-IP>

# fire 15 requests; the first 10 return 200, then 429 kicks in for the rest of the minute
for i in $(seq 1 15); do
  curl -s -o /dev/null -w "%{http_code}\n" "http://$GW/"
done

You should see ten 200s (each of which reached Service A, which called Service B) followed by 429s — the RLS's fixed-window limit of 10/min doing its job at the edge.

Verifying the internal boundary
Exec into any pod that isn't Service A and curl http://service-b.demo:8080 — you'll get 403 from B's sidecar (AuthorizationPolicy). That's "internal only" proven: unreachable from outside (no Gateway) and locked down inside (identity check).
