System Design · Storage Layer

Relational (RDS/PostgreSQL) vs Key-Value (ElastiCache/Redis)

A staff+ engineer's decision guide for choosing the primary data store — with AWS RDS for PostgreSQL and AWS ElastiCache (Redis OSS / Valkey) as the concrete implementations, both configured as a persisted store, and a full cost breakdown (instance, storage, IO, and request charges).

Pricing disclaimer. All dollar figures are representative us-east-1 on-demand rates as of early 2026 for illustrating the cost model and relative magnitudes. Exact rates change, vary by region, and depend on engine version and deployment mode. Always confirm on the AWS Pricing Calculator before quoting numbers in a real design or interview.

0TL;DR & the mental model

Interviewers at staff+ don't want "SQL vs NoSQL." They want to hear the reasoning primitives: what each store is priced on, what invariants it guarantees, and what it costs you when the workload changes. Lead with this framing:

◆ The one-sentence mental model

PostgreSQL is priced on cheap disk + compute + IO and sells you flexible querying and hard durability. Redis is priced on expensive RAM and sells you microsecond latency and high throughput on a hot working set. You are choosing which resource — durable bytes on SSD or fast bytes in DRAM — dominates your bill and your guarantees.

Everything below is downstream of that. A relational DB stores 100 GB on SSD at ~$0.12/GB-month and pulls the hot subset into a RAM buffer cache; a KV store keeps the entire dataset in DRAM priced at effectively 15–40× the per-GB cost of SSD. That single fact drives most of the pros, cons, and pricing deltas.

✦ Interview framing

The senior answer is almost never "pick one." It's "PostgreSQL as the system of record, Redis as a latency/throughput accelerator in front of it" — then justify the split by pointing at specific access patterns and their SLOs. The rest of this guide arms you to defend that split on data-model, durability, scaling, and cost grounds.

1Data model & query capabilities

PostgreSQL: schema-first, query-flexible

  • Relational model: typed columns, constraints (NOT NULL, CHECK, UNIQUE, foreign keys), normalization. The schema enforces invariants at the storage layer, not just in app code.
  • SQL + joins + aggregation: arbitrary JOIN, GROUP BY, window functions, CTEs. You can answer questions you didn't anticipate at design time — the killer feature vs KV.
  • Secondary indexes: B-tree, hash, GIN/GiST (JSONB, full-text, geo), BRIN, partial & expression indexes. Any column can become a fast access path after the fact.
  • MVCC: readers never block writers; each transaction sees a consistent snapshot. Cost: dead-tuple bloat requiring VACUUM.
  • Rich types: JSONB (semi-structured, indexable), arrays, ranges, uuid, extensions (PostGIS, pgvector for embeddings, pg_partman).

Redis: access-pattern-first, structure-rich

  • Key → value with data-structure servers baked in: Strings, Hashes, Lists, Sets, Sorted Sets (ZSET), Streams, Bitmaps, HyperLogLog, Geospatial, Bitfields. Each has O(1)/O(log N) primitives (e.g. ZADD/ZRANGEBYSCORE for leaderboards, INCR for counters, XADD for event streams).
  • No joins, no ad-hoc query engine. You model for the read: the query is the key. Access patterns must be known up front; a new one means a new key structure and a backfill.
  • Secondary access is manual: you maintain your own index keys (e.g. a SET of IDs per attribute) transactionally, or add the RediSearch module. There is no query planner.
  • Native TTL & eviction: per-key expiry (EXPIRE) and maxmemory-policy (LRU/LFU/random/volatile) — first-class, unlike Postgres where expiry is a cron/partition job.
  • Server-side atomic compute: MULTI/EXEC transactions, Lua scripts, and Functions run atomically on the shard — powerful for read-modify-write without round trips.
⚠ Gotcha — "we'll just query Redis"

Every access pattern you didn't pre-model becomes an O(N) SCAN across the keyspace or a full dataset export. KEYS * in production is an incident — it blocks the single command thread. If the business will ask unpredictable analytical questions, that's a relational (or warehouse) job, full stop.

PostgreSQL data model

  • Ad-hoc queries & reporting without pre-modeling
  • Referential integrity enforced by the DB
  • One store answers many question shapes
  • JSONB gives schema flexibility where needed
  • Schema migrations need care at scale (locks)
  • Object–relational impedance mismatch
  • Deep hot-path reads still ~ms, not µs

Redis data model

  • Purpose-built structures beat hand-rolled logic
  • Atomic counters/queues/leaderboards trivially
  • Native TTL for ephemeral data
  • Predictable O(1) latency per known pattern
  • All access patterns must be designed up front
  • No joins / no ad-hoc analytics
  • Secondary indexes are your responsibility
  • Big/hot keys create hotspots & latency spikes

2Consistency, durability & the "persisted store" question

The prompt requires both stores to persist. This is where the comparison gets genuinely technical, because "Redis with persistence" does not equal "a durable database." Understanding exactly what you get is a classic staff+ discriminator.

PostgreSQL durability — designed for zero data loss

  • Write-Ahead Log (WAL): every change is written to the WAL and fsync'd to disk before the commit is acknowledged (governed by synchronous_commit). Crash recovery replays the WAL. This is the definition of the "D" in ACID.
  • RDS Multi-AZ (instance): WAL is replicated synchronously to a standby in another AZ; commit isn't acked until the standby has it. Failover promotes the standby with near-zero RPO, RTO typically 60–120 s.
  • Read replicas: asynchronous — for read scaling, not zero-RPO durability. Replica lag is real.
  • PITR: continuous WAL archiving lets you restore to any second within the retention window.

Redis "persistence" — best-effort, not transactional

Open-source Redis offers two mechanisms; ElastiCache exposes a constrained subset:

  • RDB snapshots: point-in-time fork-and-dump of the dataset. In ElastiCache this is the backup mechanism (automatic daily + manual), stored in S3. RPO = time since last snapshot (up to 24h on defaults).
  • AOF (append-only file): logs each write; can replay on restart. Closer to WAL, but still fsync'd on an interval (everysec by default → up to 1s loss).
  • Replication: primary → replica is asynchronous. On primary failure, an acked write not yet shipped to the promoted replica is lost.
⚠ The AOF + Multi-AZ gotcha (know this cold)

On ElastiCache, AOF is not supported once Multi-AZ with automatic failover is enabled (and is unavailable on many modern node types). AWS's durability story for ElastiCache is therefore replication + snapshots + fast automatic failover — not an fsync'd log. So your realistic RPO is "last snapshot + un-replicated writes since," and it is never provably zero. If a design says "we'll persist the system of record in Redis," the correct staff+ pushback is: Redis persistence protects against process/node restarts, but its failure and durability semantics are weaker than an ACID database — size the acceptable data-loss window explicitly.

◆ Consistency nuance for cluster mode

Redis atomicity is per-shard. A MULTI/EXEC or Lua script touching keys on different shards is rejected unless you co-locate them with hash tags ({user123}:profile, {user123}:cart hash to the same slot). Cross-entity transactions that Postgres does trivially require deliberate key design in Redis — or aren't possible.

3Scaling & availability

PostgreSQL scaling

  • Vertical first: bigger instance class = more RAM/CPU/IOPS. Simple, bounded by the largest instance.
  • Read scaling: up to 15 async read replicas (RDS); route reads to a replica endpoint. Watch replica lag.
  • Write scaling: the hard problem — single writer. Options: shard in app, Citus extension, or move to Aurora (still single writer, but 15 low-lag replicas + faster failover).
  • Connections: each connection ≈ a backend process using memory; max_connections is finite. High-concurrency apps need pooling (PgBouncer or RDS Proxy) or you exhaust connections.
  • Storage: autoscaling up to 64 TiB (gp3/io2); online growth, no downtime.

Redis scaling

  • Cluster mode: data partitioned across up to 500 shards via 16,384 hash slots; scales writes and memory horizontally.
  • Read scaling: up to 5 replicas per shard; reader endpoint fans reads across them (eventually consistent reads).
  • Online resharding: add/remove shards and rebalance slots with no downtime; auto-failover per shard.
  • Connections: lightweight, multiplexed; a single node handles tens of thousands of connections cheaply vs Postgres.
  • Constraint: multi-key ops must land in one slot (hash tags). Uneven key access → hot shard; one big/hot key can't be split.
✦ The asymmetry that matters

Redis was built to scale writes horizontally; Postgres was not. If the design's headline is "5M writes/sec of simple KV data," Redis (or DynamoDB/Cassandra) is the natural fit and Postgres will need painful app-level sharding. If the headline is "complex transactions over related entities," Postgres is natural and Redis can't express it. Match the store to the hard requirement.

This headroom requirement is also a hidden cost driver (§9).

5Operational burden

Both are managed (AWS handles patching, backups, failover, host replacement). The residual work differs:

PostgreSQL — you still own

  • VACUUM/autovacuum tuning & bloat control; transaction-ID wraparound monitoring.
  • Query & index tuning (EXPLAIN ANALYZE), avoiding lock-heavy migrations.
  • Connection pooling strategy.
  • Watch: CPU, freeable memory, read/write IOPS & DiskQueueDepth, replica lag, oldest_xid.

Redis — you still own

  • Memory management: right maxmemory-policy, avoiding evictions of data you needed, headroom for fork.
  • Big-key / hot-key detection and key-design (hash tags, sharding of hot entities).
  • TTL hygiene and keyspace growth.
  • Watch: used_memory vs maxmemory, evictions, CPUUtilization (per-thread), replication lag, cache hit rate, CurrConnections.

6AWS RDS for PostgreSQL — implementation specifics

Deployment topologies

  • Single-AZ: one instance. Cheapest; no HA. Maintenance/failure = downtime.
  • Multi-AZ instance (1 standby): synchronous standby in another AZ, automatic failover. Instance cost ≈ 2× (you pay for the standby). Standby doesn't serve reads.
  • Multi-AZ DB cluster (3 instances): 1 writer + 2 readable standbys across 3 AZs, semi-sync commit, faster failover, readers usable. Higher cost (3 instances) but better read + availability.
  • Read replicas: async, cross-AZ or cross-region, promotable. Add for read scaling / DR.
  • RDS Proxy: managed connection pooler; priced per vCPU-hour of the underlying instance (adds cost) but essential for serverless/high-connection apps.

◆ The gp3 small-volume IOPS trap

A 100 GB gp3 volume is capped at 3,000 IOPS — you cannot provision more until the volume is ≥400 GiB. So a small-but-hot database often gets over-provisioned to 400–500 GB purely to unlock the 12,000-IOPS baseline, or moved to io2. This is a real design+cost decision, not a footnote. (This is why the worked example in §9 sizes storage to 500 GB.)

Aurora PostgreSQL — the relevant middle ground

Worth a sentence in any interview: Aurora keeps the Postgres wire protocol but replaces storage with a distributed, 6-way-replicated log-structured layer (auto-grows, 15 low-lag replicas, faster failover). Its cost model is different and introduces a per-request IO charge you should name:

  • Aurora Standard: lower instance/storage price + ~$0.20 per 1M IO requests — cheap until IO-heavy, then unpredictable.
  • Aurora I/O-Optimized: no per-IO charge, higher instance & storage price — predictable for IO-heavy workloads.

7AWS ElastiCache — implementation specifics

Engine: Redis OSS vs Valkey

AWS now offers Valkey (the Linux-Foundation fork of Redis 7.2, after Redis relicensed) as the default, wire-compatible engine — and prices it lower than Redis OSS (notably ~20–33% cheaper on serverless). For new builds, Valkey is usually the cost-rational choice; the data model and ops are identical.

Deployment models

  • Node-based (provisioned): you pick node type & count. Cluster Mode Disabled = one shard (1 primary + up to 5 replicas). Cluster Mode Enabled = many shards, each with its own primary+replicas. You pay per node — a 3-shard × 3-node cluster is 9 billable nodes.
  • Serverless: no nodes; AWS auto-scales capacity. You pay for data stored (GB-hour) + ECPUs (compute/requests). Fast to stand up; great for spiky/unknown load; pricier per-unit at steady high load.
  • Multi-AZ + auto-failover: place replicas in other AZs; promotes on primary loss (recall §2: this replaces AOF as the durability story).
  • Data tiering (r6gd nodes): keeps hot data in RAM and spills cold data to local NVMe SSD — lowers $/GB for large datasets at some latency cost for cold hits. The main lever to make "big Redis" affordable.

Persistence configuration (per the prompt's requirement)

  • Enable automatic backups (daily snapshot to S3) + retention; take manual snapshots before risky ops.
  • Enable Multi-AZ with auto-failover (this is the practical durability mechanism).
  • Accept that RPO is bounded by snapshot interval + replication lag — design the app to tolerate it (idempotent writes, replay from the SoR).

◆ Why the per-GB gap is so large

Redis stores every byte in DRAM. A cache.r6g.2xlarge gives ~52.8 GiB usable for ~$0.824/hr = ~$601/mo, i.e. ~$11.4 per GB-month of usable RAM — and you typically double that for a replica and can only fill it ~70%, pushing effective cost toward ~$30+/GB-mo of durable capacity. RDS gp3 SSD is ~$0.115/GB-mo. That's a ~100–250× storage-cost ratio. Redis only "wins" when the value of µs-latency/high-throughput on the hot set exceeds that premium — which is true for caches and false for bulk storage.

Commitment discounts (don't quote on-demand as if it's the real bill)

  • RDS: Reserved Instances / Savings Plans — ~40% (1-yr no-upfront) to ~60–65% (3-yr all-upfront).
  • ElastiCache: Reserved Nodes — similar tiers (~30–60%).
  • Serverless: no commitment discount (that's the trade for elasticity).

◆ Node-based vs Serverless decision rule

Steady, predictable, high-throughput → provisioned nodes (you amortize a fixed node across huge request volume at $0/request). 11Decision framework

Choose RDS PostgreSQL when…

  • It's the system of record — losing an acked write is unacceptable (payments, orders, user accounts).
  • Data is relational with cross-entity transactions / referential integrity.
  • Query shapes are diverse or unknown (reporting, ad-hoc, joins, aggregations).
  • Dataset is large relative to hot set — you want cheap SSD for the bulk and RAM only for the working set.
  • Write volume fits a single (large) writer.

Choose ElastiCache Redis when…

  • You need µs latency / very high QPS on a known access pattern.
  • The workload is cache, session store, rate limiter, leaderboard, real-time counter, pub/sub, queue/stream, or other derived/ephemeral state.
  • Data is simple KV and the working set fits (affordably) in RAM.
  • You need to scale writes horizontally and can design keys around hash slots.
  • Some data-loss window is tolerable (or the SoR can replay).
✦ The default staff+ answer: use both (CQRS-lite)

PostgreSQL is the durable system of record; Redis is a read-through / write-through cache and real-time layer in front of it. Postgres owns correctness and arbitrary queries on cheap storage; Redis absorbs the hot read traffic and latency-critical ops. You get Postgres's durability and Redis's speed, and you only pay DRAM prices for the hot slice — not the whole dataset. Name the cache strategy (cache-aside vs write-through), the TTL, and the invalidation plan, and you've answered the question at staff level.

Anti-patterns to call out

  • anti-pattern Redis as the sole system of record for critical data — accepting a non-zero RPO you didn't quantify.
  • anti-pattern Storing a large cold dataset entirely in Redis — paying DRAM prices for bytes you rarely read (use data-tiering or keep it in Postgres/S3).
  • anti-pattern Ad-hoc analytics on Redis via KEYS/SCAN — that's a relational/warehouse job.
  • anti-pattern Postgres as a high-churn cache — hammering it with ephemeral writes creates bloat/vacuum pressure Redis handles natively with TTL.

12Interview cheat-sheet — rapid-fire

"Why is Redis more expensive per GB than RDS?" Redis holds every byte in DRAM (~$11/GB-mo per copy, doubled for a replica, filled only ~70% → ~$30+/GB-mo effective); RDS keeps bulk on SSD at ~$0.115/GB-mo and caches only the hot set in RAM. A ~100–250× storage-cost ratio. You pay the Redis premium only for latency/throughput, not for storage.
"Both must persist. Is Redis durability equivalent to Postgres?" No. Postgres = synchronous WAL fsync + sync Multi-AZ standby → ~0 RPO. ElastiCache Redis = async replication + periodic S3 snapshots (AOF unsupported with Multi-AZ failover) → non-zero RPO. Redis persistence survives restarts but is not transactional durability; quantify the acceptable data-loss window.
"Where does 'IO cost' and 'request cost' show up?" RDS: IO = gp3 provisioned IOPS/throughput beyond baseline, or io2 per-provisioned-IOPS; standard RDS has no per-request charge (Aurora Standard adds ~$0.20/1M IO). Node-based Redis: zero IO and zero request cost — it's all in the node price. Serverless Redis: no IO line, but ECPU is a per-request charge (~$0.0023–0.0034/M).
"When node-based vs serverless ElastiCache?" Steady/high sustained throughput → provisioned nodes (fixed cost, $0/request). Spiky/bursty/idle-heavy/unknown → serverless (per-ECPU + scale-to-near-zero). Serverless storage at ~$0.084/GB-hr is costly for large always-on sets.
"How do they scale writes?" Postgres: single writer — vertical, or app-sharding / Citus / Aurora. Redis: horizontal via cluster mode (hash slots, up to 500 shards) — built for write scale-out, but multi-key ops need co-located keys (hash tags).
"Name a Redis operational failure mode." Single command thread per shard → one O(N) command (e.g. KEYS *, big SMEMBERS) stalls all clients on that shard; and RDB snapshot fork() can transiently double memory (COW) — hence the 25–35% headroom rule (a cost driver too).
"Cut the Redis bill for a large dataset without moving off Redis?" Data-tiering (r6gd) — hot in RAM, cold on local NVMe; fewer/smaller RAM nodes; Reserved Nodes (~-50%); switch engine to Valkey (~20–33% cheaper on serverless); shorten TTLs / evict aggressively so you provision for the true working set, not all-time keys.
