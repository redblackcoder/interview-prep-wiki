0 · How to use this guide

This guide is built for a staff+ system-design interview where rate limiting is the topic — either as the whole prompt ("design a rate limiter") or as a component of a larger design ("design an API gateway / a public API / a payment system"). It is deliberately opinionated and code-grounded.

The reference implementation is Envoy (the data plane used by Istio) and the Envoy global rate limit service — the exact Go/gRPC service whose source lives in this repository. Wherever you see a green REPO callout, it points at real code you can cite in an interview.

The one-sentence mental model
A rate limiter answers one question — "has identity X exceeded N events per time-unit T?" — and the entire design space is about where you keep the counter (in-process vs shared store), how you shape the window (fixed, sliding, bucket), and what you trade when the counter is wrong (accuracy vs latency vs availability).

Read top-to-bottom once; then use §12 (cheat sheet) and §11 (Q&A) for revision.

1 · Why rate limit — the requirements behind the algorithm

Before algorithms, get crisp on why, because it drives every trade-off later. Interviewers probe this to see if you reach for a limiter reflexively or reason about it.

GoalWhat it protectsDesign implication
Overload / stabilityYour own backends from thundering herds, retry storms, traffic spikesMust fail closed enough to protect but degrade gracefully; latency budget is tiny
FairnessOne noisy tenant from starving others (multi-tenant SaaS)Needs per-identity keys (tenant, API key, user); global coordination matters
Cost controlMetered downstreams (LLM tokens, 3rd-party APIs, DB IOPS)Quota semantics (per-day), accuracy matters more than latency

1.1 Rate limiting is one tool in a family — meet the neighbours

Interviewers probe whether you see rate limiting in context. It belongs to a family of load-management techniques that all answer one question — "should we do this work right now?" — but each uses a different signal and acts at a different point. Here's the family, roughly ordered from "front door" to "last resort". You don't deploy one; you combine them.

TechniqueWhat it actually doesSignal it watchesProactive / reactive
Admission controlDecides at the entry point whether to accept a request or connection at all. This is the umbrella idea — rate limiting is one specific kind of admission control.Capacity, caller priority, or a policyProactive
Rate limitingCaps events per unit of time for a given identity (this guide's topic). "1000 requests / day / API key."A count vs a fixed thresholdProactive
Concurrency limitingCaps how many requests are in flight at the same time — not their rate. "At most 100 requests being processed at once." It self-throttles: if a downstream slows down, in-flight slots stay occupied longer, so new work is rejected automatically.Number of in-flight requestsHybrid
Circuit breakingWhen a downstream is failing or slow, stops sending it traffic entirely for a cool-down, then sends a trickle to test if it recovered. Prevents one sick service from dragging down everything calling it (a "cascading failure").Downstream error / latency rateReactive
Load sheddingUnder genuine overload, proactively drops the least important work (e.g. background refreshes before checkout) to keep the system alive at all.System health: CPU, queue depth, latencyReactive

Two more terms you'll hear next to these — worth being able to define:

  • Backpressure — rather than swallowing work it can't handle, a component signals "I'm full, slow down" back up the call chain (usually by letting a bounded queue fill and refusing new entries). Rate limiting is one way to apply backpressure at the edge of a system.
  • Adaptive concurrency — a concurrency limit that tunes itself from observed latency instead of a hard-coded number: when latency climbs, it reads that as congestion and lowers the limit automatically. The two canonical examples are Netflix's concurrency-limits library and TCP congestion control (the TCP Vegas algorithm infers congestion from rising round-trip time) — both use latency as the feedback signal instead of a fixed cap.
Staff-level framing
The distinction to land: rate limiting is proactive and static — it enforces a fixed contract keyed on identity ("this key gets 1000/day") no matter how healthy the system is right now, and it only governs the rate of arrivals — it does nothing about a request that turns slow once admitted. The others further down the table are reactive — they respond to live system state (concurrency limiting does this implicitly; circuit breaking and shedding do it explicitly). So a strong answer places the limiter among these tools instead of treating it as the only lever — e.g. "a per-tenant rate limit for fairness, plus adaptive concurrency to survive a downstream that gets slow in a way the rate limit can't see."

2 · The five algorithms

Every limiter is one of these five (or a hybrid). Know the counter each one keeps, its memory cost, its burst behavior, and its failure edge.

2.1 Fixed window counter

Divide time into fixed buckets (e.g. each wall-clock minute). Keep one integer per (key, bucket). Increment on each request; reject when the counter exceeds the limit. The bucket resets when the clock rolls into the next window.

# counter keyed by (identity, floor(now / window))
allow(key, now):
    bucket = floor(now / W)
    c = INCR(key + ":" + bucket)
    EXPIRE(key + ":" + bucket, W)   # TTL so old buckets self-clean
    return c <= LIMIT
  • Memory: O(1) per active key — a single counter. Cheapest of all.
  • Burst flaw: the classic 2× boundary burst. With a limit of 100/min, a client can send 100 at 00:00:59 and 100 at 00:01:00 — 200 requests in ~1 second, all "legal".
  • This is what the RLS in this repo uses — see §5.3. It's chosen precisely because it's O(1) and needs only atomic INCR, which distributes trivially.

2.2 Sliding window log

Store a timestamp for every request in a sorted set. To decide, drop entries older than now − W and count what remains. Perfectly accurate, no boundary burst.

  • Memory: O(N) per key where N = requests in the window — expensive and unbounded under attack (the log itself becomes a DoS vector).
  • Use when: low request volume, high accuracy need (e.g. "5 password resets/hour").

2.3 Sliding window counter (approximation)

The pragmatic middle ground. Keep two fixed-window counters (current + previous) and weight the previous one by how far you are into the current window:

est = curr + prev * (1 − elapsed_in_window / W)
allow = est < LIMIT
  • Memory: O(1) — two counters. Smooths the boundary burst to a small over/undershoot (bounded, provably within a few %).
  • This is what Cloudflare famously described using at the edge; a great "I'd improve fixed-window like this" answer.

2.4 Token bucket

A bucket holds up to B tokens and refills at rate r tokens/sec. Each request removes a token; empty bucket ⇒ reject (or wait). State is just (tokens, last_refill_ts), refilled lazily on access.

  • Allows controlled bursts up to B while enforcing a long-run average r. This is the model humans usually mean by "rate limit".
  • Memory: O(1). This is what Envoy's LOCAL limiter uses (§4.1–4.2).

2.5 Leaky bucket

Requests enter a FIFO queue that drains at a fixed rate. Overflow ⇒ reject. Output is perfectly smooth (no bursts pass through) — think traffic shaping. Token bucket permits bursts; leaky bucket forbids them. Distinguishing these two crisply is a common interview filter.

3 · Two axes: Local vs Global, L4 vs L7

The single most useful framing for this topic. Every real deployment is a point on a 2×2 grid, and Envoy lets you occupy several cells at once.

Axis A — where the counter lives

  • Local: counter is in-process, per proxy instance. Zero network hop. But with M proxies the effective limit is M × configured unless you divide.
  • Global: counter is in a shared store (Redis) fronted by a service. One authoritative count across the fleet, at the cost of an RPC per decision.

Axis B — what layer you inspect

  • L4 (transport): you see connections/bytes, IP:port, SNI. Cannot see HTTP path, method, headers, JWT claims.
  • L7 (application): you see the full HTTP request — path, method, headers, cookies, mTLS/JWT identity. Enables per-API, per-user policy.
The pattern that wins interviews
Real systems layer these: a cheap local limiter as a first line of defense (protects even if the global store is down) plus a global limiter for accurate fleet-wide fairness. Envoy is explicitly designed for this — local descriptors and global descriptors coexist on the same route.

4 · The Envoy / Istio enforcement model

Istio's data plane is Envoy. When you "rate limit in Istio", you are configuring Envoy filters (Istio just generates that config from its CRDs — which we're deliberately skipping). So everything below is Envoy mechanics.

Envoy processes each request through a filter chain. Rate limiting is implemented as filters at two levels of that chain:

  • A network (L4) filter — sees connections.
  • An HTTP (L7) filter — sees requests, sits in the HTTP connection manager's chain.

Each of those has a local variant (decision in-process) and a global variant (decision delegated to an external RLS over gRPC). That gives the three practical modes below.

4.1 L4 local rate limiting (connection-level)

The network filter envoy.filters.network.local_ratelimit runs a token bucket per listener, entirely in-process. It limits the rate of new L4 connections (or generic bytes) accepted.

  • Sees: connections only. No HTTP semantics. Cannot distinguish /login from /health.
  • Cost: a few atomic ops — sub-microsecond. No allocation, no I/O.
  • Use for: a coarse blast-door — cap total connection churn to a service to protect the accept loop and TLS-handshake cost, independent of any backend.
Fleet math
A local L4 bucket of "1000 conns/s" on 20 sidecars admits up to 20,000/s fleet-wide. Local limits are per instance; you either accept that or divide the limit by replica count (which then breaks on autoscale — a classic gotcha).

4.2 L7 local rate limiting (per-route, no external call)

The HTTP filter envoy.filters.http.local_ratelimit also runs a token bucket in-process, but now with full HTTP visibility. You can attach it per virtual host or per route, so different paths get different buckets — the "per-API limit with no external service call" the prompt asks about.

  • Sees: path, method, headers, downstream identity. So you can say "POST /search → 10 rps bucket, burst 20" while "GET /static/*" is unlimited.
  • Token-bucket params: max_tokens (burst), tokens_per_fill + fill_interval (refill rate).
  • Still local: each Envoy has its own bucket. Great for a fast, dependency-free first tier. It keeps working even if Redis/RLS is down.
  • Envoy can also enforce local limits keyed by descriptors (the same descriptor concept the global path uses), so you can do a limited amount of dimensional limiting without any network hop.

How "per-API" is expressed: Envoy matches the request to a route (by path prefix / regex / header), and the route carries its own local_ratelimit config. So the "path → policy" mapping is just route matching — no external lookup, the bucket is selected by which route matched.

4.3 L7 global rate limiting (delegated to the RLS)

The HTTP filter envoy.filters.http.ratelimit does not decide anything itself. On each request it:

  1. Builds a list of descriptors — ordered key/value tuples derived from request attributes (the actions configured on the route: request headers, remote address, path, JWT claims, etc.).
  2. Calls the external RLS over gRPC: ShouldRateLimit(domain, [descriptors]).
  3. Enforces the returned code: OVER_LIMIT ⇒ Envoy responds 429 locally (the upstream is never contacted); OK ⇒ request proceeds.

This is the path implemented by the service in this repository. The rest of the guide dissects it.

Why split the decision out of Envoy?
Because the counter must be shared across every Envoy in the fleet to be accurate, and because rate-limit policy changes far more often than proxy config. Externalizing gives one authoritative counter (in Redis) and lets policy hot-reload independently of the data plane.

5 · The global RLS — architecture (this repo)

envoyproxy/ratelimit is a Go / gRPC service that reads a rate-limit config, receives descriptor-based requests from Envoy, composes cache keys, and atomically increments counters in Redis (or Memcached). It returns OK / OVER_LIMIT per descriptor.

5.1 The gRPC contract

The entire service is one RPC. Envoy sends a domain and a list of descriptors; the service returns an overall code plus a per-descriptor status.

Repo · src/service/ratelimit.go
ShouldRateLimit() wraps shouldRateLimitWorker(). Note the design choices in the worker:
  • It asserts domain != "" and a non-empty descriptor list, then snapshots config under an RWMutex (GetCurrentConfig()) so a concurrent hot-reload can't tear the read.
  • The overall code is OVER_LIMIT iff at least one non-quota descriptor is over — a logical AND of "everything must be OK". (Quota-mode descriptors are the exception: they only trip the overall code if all quota descriptors are over.)
  • Errors are handled via recover() — a Redis panic becomes a gRPC error, and the caller (Envoy) decides fail-open vs fail-closed.
// The heart of the per-descriptor loop (paraphrased from ratelimit.go)
responseDescriptorStatuses = cache.DoLimit(ctx, request, limitsToCheck)
for i, status := range responseDescriptorStatuses {
    if status.Code == OVER_LIMIT && !isQuotaMode {
        failedRateLimitDescriptors++      // any one trips the whole request
    }
}
if failedRateLimitDescriptors > 0 { finalCode = OVER_LIMIT }

5.2 The descriptor tree — how policy is modeled

This is the conceptual core and a great whiteboard topic. A descriptor is an ordered list of key/value entries describing one request dimension, e.g.:

domain: "messaging"
descriptor: [ (key=to_number, value=+1900...),
              (key=source_cluster, value=proxy) ]

The config is a tree of descriptors. Envoy sends the runtime values; the RLS walks the tree to find the most specific matching limit.

Repo · src/config/config_impl.go → GetLimit()
The lookup is a nested-map traversal, not a linear scan:
  • Config loads into nested map[string]*rateLimitDescriptor. Each entry is keyed by key_value (specific) with a fallback to just key (a default that matches any value).
  • For each descriptor entry it tries key_value first, then key, then wildcard patterns (pre-split on * at load time so matching allocates nothing per request — see wildcardMatch()).
  • It descends level by level; the deepest matched rate_limit wins. This is O(depth), typically 1–3 map lookups.
  • An Envoy-supplied limit override in the request short-circuits config entirely — the caller can dictate the limit.

This tree is exactly how you get "per-API" policy in the global path: a descriptor like (path, /v1/search) nested under (api_key, X) lets you express "10k/day per key, but only 100/min on the search path". Contrast with the local L7 path (§4.2) where "per-API" comes from route matching instead.

5.2a Where descriptors come from — how "client identity" is defined

A natural question: when Envoy rate-limits a caller, what is the caller's identity — its IP? Its service name? A certificate? The answer is the single most important thing to understand about this whole mechanism, and it's slightly counter-intuitive:

Envoy has no built-in notion of "client identity"
Look back at the RLS in this repo — GetLimit() receives a domain and a list of descriptors and matches them against the config tree. It never inspects an IP, a certificate, or a "who". The service is identity-agnostic. Identity is not intrinsic — it is composed at config time by Envoy from request and connection attributes, using constructs called rate limit actions (descriptor generators) attached to the route (L7) or the network filter (L4). Whatever attributes you extract into descriptors becomes the identity. Extract IP → identity is IP. Extract an API key → identity is the API key. Extract the caller's mTLS principal → identity is the service. There is no privileged "client" field; the limiter keys on whatever you told Envoy to put in the descriptor.

So "IP address or virtual-server identity?" is a false choice — they're just different actions you can select per limit. The menu of actions that produce descriptor values:

Action (descriptor generator)Value it emitsKind of identityTrust / stability
remote_address / masked_remote_addressclient IP, or a CIDR-masked subnetnetwork identitySpoofable at the edge; IPs are ephemeral
request_headersvalue of a header (x-api-key, authorization, :path, x-user-id)app / user / API-key identityOnly as trustworthy as the header — needs auth to populate/verify it
source_clusterthe local Envoy's own service-cluster nameservice identity of this proxyStable, but direction-sensitive (see below)
destination_clusterthe upstream cluster being routed toidentity of the callee / resource, not the callerFor "protect this resource" limits
metadataa value from dynamic/connection metadata — e.g. the mTLS peer principal or a verified JWT claim populated by an earlier filtercryptographic caller / user identityStrongest — verified, not spoofable
generic_keya static string configured on the route"this route / tenant" as a wholeFixed
header_value_matcha value emitted only when header conditions matchderived (e.g. method == GET)Derived from request shape

It also helps to separate three things people conflate under "identity": the caller (IP, source_cluster, mTLS principal, API key), the callee / resource (destination_cluster, virtual host, path — "protect this service"), and a composite (caller × path, tenant × endpoint — which is exactly the nested descriptor tree from §5.2).

Edge (external ingress) vs. mesh (internal east-west)

The available and trustworthy signals differ completely by traffic direction — this is the crux of your question.

External / ingress gateway

Clients are anonymous and untrusted (browsers, third parties). There is no mTLS peer identity. Identity is typically:

  • Client IP via masked_remote_address,
  • an API key / token from a header — often after a JWT or ext_authz filter validates it and the metadata action reads the verified claim, or
  • a generic_key per route.

Internal mesh gateway / sidecar

The "client" is another workload, authenticated by mTLS. With Istio each workload carries a verified SPIFFE identity (e.g. spiffe://cluster.local/ns/payments/sa/checkout) bound to its service account.

  • Key on that principal via the metadata action (or coarsely via source_cluster).
  • It's cryptographically verified — not spoofable, far better than any edge signal.
  • Pod IP is a poor key here — pods churn and autoscale, so remote_address is ephemeral and meaningless east-west.
The X-Forwarded-For trap (the #1 edge mistake)
At an edge gateway the immediate TCP peer is usually a cloud L4 load balancer (NLB/ELB), not the real client — so remote_address returns the LB's IP unless you configure Envoy's trusted-hop handling (xff_num_trusted_hops, or Proxy Protocol) to peel the real client IP out of X-Forwarded-For. Get it wrong one way → every client shares one bucket (the LB's IP) and the limit collapses your whole API into a single counter. Get it wrong the other way (blindly trusting a client-supplied X-Forwarded-For) → an attacker rotates fake XFF values to mint infinite fresh identities and evades the limit entirely. IP-as-identity is only as good as your trusted-hop config.
Direction caveat on source_cluster
source_cluster always emits the local Envoy's own service-cluster, regardless of traffic direction. On a caller's outbound sidecar that's the caller (useful); on the callee's inbound sidecar that's the callee itself (useless as caller-identity). So to limit "requests from service X" at the receiving end, you must key on the mTLS peer principal via metadata, not source_cluster.
The compressed rule
At the edge, identity is a spoofable network/header signal you must harden (trusted hops, upstream auth); inside the mesh, identity is a verified cryptographic service principal you should prefer over IP. Same RLS, same descriptor mechanism — only the source and trustworthiness of the descriptor values change. This is why the RLS being identity-agnostic is a feature: one service correctly limits both a public API keyed on API-key and internal service-to-service traffic keyed on SPIFFE identity, with no code change — only different actions on the two Envoys.

5.2b Identifying the external client — authenticated vs anonymous

§5.2a said identity is "whatever attribute you extract." But which attribute is trustworthy hinges on one question the interview will press: is the caller authenticated? The answer flips the whole problem.

For an authenticated API, IP is almost irrelevant
When the caller presents an API key / OAuth token / account ID (Twitter's API, any SaaS backend), the credential is the identity. You key the limit on it directly. A VPN changes the IP but not the token, so IP-hopping does nothing to evade an API-key limit. IP here is only a secondary anomaly signal (one key from 10,000 IPs → credential sharing/theft; one IP minting 10,000 keys → an abuse ring). This is why the VPN-hopping worry (§7.5) mostly evaporates for authenticated surfaces.

Unauthenticated surfaces are where IP actually matters — login, signup, password reset, token issuance, anonymous reads. There's no account yet, so a network-derived key is the best coarse identity you have — and exactly where raw IP betrays you. The networking fundamentals:

FundamentalWhy raw IP fails / what to do
CGNAT / NATCarrier-grade NAT puts thousands of mobile users behind one public IPv4; an office or VPN exit is one IP for many humans. IP-as-identity → false positives (throttle innocents) and false negatives (one user across many IPs).
ASN / BGPEvery IP belongs to an Autonomous System (network operator). Distinguish residential/eyeball ASNs from datacenter/hosting ASNs (AWS, OVH) and known VPN/Tor egress. Consumer traffic from a datacenter ASN is inherently suspicious — rate-limit or challenge it far harder. Commercial VPNs have enumerable egress ranges you can buy as threat intel.
Subnet aggregation & the IPv6 trapLimit per /24 (IPv4) or per /64 (IPv6), not per exact address. A single IPv6 customer is handed a whole /64; limiting per /128 lets them rotate for free within their own allocation. The /64 is the "one customer" unit.
Real client IP recoveryThe source IP you see is the last hop (LB/CDN), not the client. Reconstruct via X-Forwarded-For with a correct trusted-hop count, RFC 7239 Forwarded, or Proxy Protocol (L4). Wrong config → bucket everyone as the LB (limit collapses) or trust attacker-supplied XFF (limit evaporates). See the §5.2a XFF trap.

Beyond IP — identifying the source when IP is defeatable

Since a determined attacker rotates IPs (VPNs, residential-proxy networks), layer in signals that survive IP rotation:

  • TLS fingerprinting (JA3 / JA4) — the ClientHello (cipher suites, extensions, curves, and their order) fingerprints the client software/stack. A given bot or library has a characteristic JA4 hash regardless of IP, so 1,000 rotating IPs may present one telltale fingerprint. The single most useful "who is this really" signal for bot/abuse detection.
  • TCP/IP stack fingerprinting (p0f-style) — TTL, window size, TCP options reveal OS/stack; can expose that "1,000 IPs" are all the same tooling.
  • HTTP/2 fingerprinting & header order, and for browsers device fingerprinting (canvas/fonts) and device IDs / cookies for stickiness across IPs (clearable → weak alone).
The honest admission — and what to do instead
You cannot perfectly identify the source of an unauthenticated request over the modern internet — NAT, VPNs, and residential proxies make it fundamentally ambiguous. So the goal shifts from identify to raise attacker cost + composite scoring + graceful degradation: (1) rate-limit simultaneously per-account, per-IP, per-/64, per-ASN, and per-JA4, tripping on the tightest that matches (a hierarchy, not one key); (2) use ASN reputation as a multiplier — datacenter/VPN ASNs get a fraction of the residential budget; (3) on weak/ambiguous signals degrade to a challenge (CAPTCHA, proof-of-work, step-up auth) rather than a hard 429 — so a shared-IP false positive costs a real user a challenge, not an outage.

5.3 The algorithm: fixed-window over an atomic counter

The RLS uses a fixed-window counter (§2.1). This is a deliberate, defensible choice — understanding why is the interview payoff.

Repo · src/redis/fixed_cache_impl.go → DoLimit()
The counter lives entirely in Redis; the RLS is stateless. Per descriptor it pipelines two commands: 
pipeline.INCRBY(key, hitsAddend)   // atomic add, returns new count
pipeline.EXPIRE(key, unitSeconds)   // self-cleaning window
The returned value after INCRBY is limitAfterIncrease; if it exceeds requests_per_unit the descriptor is OVER_LIMIT. Because INCRBY is atomic, concurrent Envoys racing on the same key are serialized correctly by Redis — no lost updates, no read-modify-write race.

Key properties to state out loud:

  • Why fixed window and not sliding? Because it reduces to a single atomic integer op that any shared store supports natively. Sliding-log would need a sorted set + trimming per request (O(N) memory, more round-trips) — far heavier at the RLS's throughput.
  • The window is derived from the key, not stored. The current bucket is baked into the cache key via time flooring (next section), so "which window am I in" needs no extra state and old windows simply expire.
  • Accepts the 2× boundary burst as a known trade — mitigated in practice by short units (per-second limits) and jittered expiry (§5.6).
  • hitsAddend: a request can cost more than 1 (weighted requests — e.g. a batch of 50). Default is 1; the counter increments by the addend. A zero addend means "check but don't consume".

5.4 Cache key construction & time bucketing

The cache key is the algorithm's window. This is the most elegant piece to explain on a whiteboard.

Repo · src/limiter/cache_key.go + src/utils/time.go
A key is prefix + domain + "_" + (key_value pairs...) + "_" + windowStart, where the window is computed by flooring the current unix time to the unit divider: 
// UnitToDivider: SECOND→1, MINUTE→60, HOUR→3600, DAY→86400...
divider = UnitToDivider(unit)
windowStart = (now / divider) * divider   // integer floor to bucket
So a per-minute limit on (database, users) yields keys like mongo_cps_database_users_1699488000, then ..._1699488060 the next minute. When the clock rolls into a new bucket, the key changes automatically, the counter starts fresh, and the old key's TTL cleans it up. No sweeper, no reset job. 
# Two requests, same identity, straddling a minute boundary
09:00:59  key = ..._1699488000   INCRBY → 100   OK
09:01:00  key = ..._1699488060   INCRBY → 1     OK   # fresh bucket = the 2× burst

5.5 The local over-limit cache — a latency optimization

An optional in-process cache (freecache) stores only keys already known to be over the limit for the remainder of their window. This is subtle and worth calling out as a mature design touch.

Repo · src/limiter/base_limiter.go
When a key goes over limit, the RLS writes it to the local cache with a TTL equal to the remaining window. On subsequent requests, IsOverLimitWithLocalCache() is checked before touching Redis — an over-limit key returns 429 immediately with no network hop. The TTL logic is deliberately tied to the unit so that when the time bucket rolls over (key changes), the stale over-limit entry naturally loses effect.
Why only cache the over-limit verdict?
Because it's the only verdict that's safe to cache without weakening the limit. Caching "OK" locally would let each proxy under-count (it'd skip the shared INCR), breaking global accuracy. Caching "OVER" only ever rejects traffic that Redis already said to reject — it can never let excess traffic through. It converts the expensive part of an attack (a hot, already-blocked key) from N Redis round-trips into N local map hits. Asymmetric caching like this is a strong signal of senior thinking.

5.6 The Redis data path — pipelining, pooling, sharding

Repo · src/redis/driver_impl.go, fixed_cache_impl.go, settings.go
  • Pipelining: all descriptors in one request are batched into a single pipeline (INCRBY+EXPIRE per key), so a multi-descriptor request is one Redis round-trip, not N. In cluster mode commands are grouped by key/slot and can run with bounded parallelism (RedisClusterPipelineParallelism).
  • Connection pool: fixed-size pool (radix v4), blocks when exhausted (WAIT) — you size REDIS_POOL_SIZE against concurrency and use context timeouts for fail-fast.
  • Expiry jitter: ExpirationJitterMaxSeconds (default 300) randomizes TTLs so millions of keys don't expire in the same instant — avoids a synchronized cache-cliff / thundering herd on Redis.
  • Per-second split: optionally a separate Redis for per-second limits (REDIS_PERSECOND), because per-second keys have very different churn/hotness than per-day keys and you don't want them competing for the same instance.
  • Cluster / Sentinel: supports single, sentinel (HA failover), and cluster (sharded) topologies. Keys shard by the hash of the full cache key, so a given identity+window always lands on one shard — preserving atomicity of its counter.
  • READONLY recovery: after a failover, a demoted master keeps connections open that now reject writes; the pool can close-on-READONLY to re-dial the new master.

Memcached alternative: the repo also ships a Memcached backend. Since memcache has no implicit-create-on-increment, it does an increment→add→increment dance, and it does the increment asynchronously after responding (reads via GetMulti in the critical path, writes in the background). That trades a little accuracy (a race window) for lower tail latency — a good contrast point on consistency vs latency.

The fail-open trap
Fail-open is the safe default for stability limiters (you'd rather serve than 429 everyone when Redis blips). 7 · Distributed correctness — the hard parts

Atomicity / race conditions

The naive GET; if ok INCR has a read-modify-write race: two proxies both read 99, both allow, count hits 101. The RLS avoids it by using INCR's return value as the decision — the increment and read are one atomic op. State this explicitly; it's the #1 correctness bug in home-grown limiters.

Clock skew

Fixed-window buckets are computed from each RLS instance's local clock (now / divider). If RLS instances disagree on the time, they may bucket the same request differently. Mitigations: NTP-synced hosts, and coarse-enough units that skew (tens of ms) is negligible vs the window (seconds+).

Hot keys

A single very popular identity (one giant tenant, or an attack on one key) concentrates all its traffic on one Redis slot — you can't shard a single counter. Mitigations: the local over-limit cache (absorbs the blocked case), share_threshold vs per-value keys (control cardinality), and for extreme cases request-count sampling or splitting a logical limit into K sub-counters summed periodically.

Approximate/eventually-consistent variants

At extreme scale some systems relax global accuracy: each node enforces a local share of the global budget (e.g. 20 nodes, 1000/s total → 50/s each) and periodically reconciles with a central view — either by reporting to a coordinator, or by gossip (nodes exchange their local counts peer-to-peer so each converges on an approximate global total). You trade exactness for removing the per-request round-trip: between reconciliations, nodes have a stale picture, so the true total can briefly overshoot. Worth naming as "how I'd scale past a single Redis's throughput".

Likely follow-up
"Your Redis does 200k ops/s but you need 2M decisions/s — what now?" → (1) cut round-trips: batch descriptors, local over-limit cache; (2) shard by key across a Redis Cluster (works because each counter is independent); (3) push down to local per-node budgets with async reconciliation; (4) relax the algorithm to sliding-counter to reduce store pressure. Name the trade each makes.

7.5 · Global / multi-region rate limiting

The hardest version of the question: "Rate-limit a globally-distributed API (say Twitter) by API key, so a user can't bypass the limit by VPN-hopping across regions. Surely you're not proposing a globally-consistent Redis?" The trap is that this sounds like a hard consistency problem. It mostly isn't — if you get two framings right.

Framing 1 — VPN-hopping is beaten by identity keying, not by counter consistency
The bypass exists only if you partition the counter by geography (independent per-region limiters with no cross-region accounting). Key the counter on identity (the API key) instead, map that key to one logical global count, and hopping us→eu→asia draws down the same total everywhere. For an authenticated API the identity is the credential (§5.2b) — a VPN can't change it. So "make the global counter strongly consistent so hopping can't help" is solving the wrong problem with the most expensive tool.
Framing 2 — globally consistent ≠ globally accurate
Consistent (linearizable) is expensive and unnecessary; accurate (eventually convergent) is cheap and sufficient. Ask the business question: if the limit is 1000/hr, does anything break if an attacker briefly gets 1010 before regions converge? Almost never. The first design move is choosing the consistency model — "bounded overshoot is fine" — not choosing a store. That choice dissolves the latency problem below.

The pushback, made precise

A synchronous global counter on the hot path is genuinely non-viable — but because of cross-region RTT (us↔eu ≈ 80 ms, us↔asia ≈ 150–250 ms), not because of Redis. Adding that to every single-digit-ms API call is a non-starter, and it makes availability worse (every region now depends on a far quorum). And note: "globally consistent Redis" is nearly a category error — Redis Cluster replicates asynchronously; it does no cross-region consensus. So the strongly-consistent thing being rejected doesn't exist in Redis anyway. Reject it — but for the RTT reason, and know that an eventually-consistent global Redis (active-active) very much is viable.

Recommended architecture — tier consistency by the cost of overshoot
  • Hot path is always local — in-region Redis, or an in-process token bucket for the very hottest keys (tier-1 from §6).
  • Most limits (throughput/fairness, where +5% overshoot is harmless) use CRDT active-active — zero request-path RTT, tiny bounded overshoot.
  • A few security-critical, low-volume limits ("10 password resets/hr/account") that must be tight use home-region pinning — accept one cross-region hop because volume is low and correctness matters.
Different consistency for different limits, justified by blast radius — that distinction is the staff-level signal. State the guarantee out loud: "global limit enforced within replication lag; worst-case transient overshoot ≈ (peak cross-region QPS for a key) × (replication lag) — a rounding error for a 1000/hr limit."
The one-liner that lands it
This is CAP applied to counting. You can't have exact-global + low-latency + partition-tolerant, so you relax exactness to bounded overshoot — the dimension the business cares least about. Hopping is defeated by keying on identity; the counter only needs to be approximately globally accurate, which is cheap.

8 · Scaling, operability & the "-ilities"

Stateless RLS ⇒ horizontal scale

The RLS holds no counter state (only cached config + the over-limit cache). Scale it by adding replicas behind the gRPC LB; all share the same Redis. This is why the design externalizes state to Redis.

Config delivery

Two providers: file (watched via runtime, hot-reloaded) and xDS management server (config streamed over gRPC; SotW = "state of the world", meaning each update pushes the complete config rather than an incremental diff). Config swaps are atomic under an RWMutex; a bad config keeps the last-good one. Policy changes need no redeploy.

Observability

Rich per-limit stats: total hits, over-limit, near-limit, shadow-mode, within-limit — via statsd/DogStatsD/Prometheus. near_limit (default 80% ratio) is the early-warning metric you alert on before customers hit 429s.

Safe rollout — shadow mode

shadow_mode (per-limit or global) runs the full pipeline — counts, stats, cache — but always returns OK. You deploy a new limit, watch the "would-have-blocked" stat, then enforce. Essential for not paging yourself with a mis-tuned limit.

9 · Advanced features worth name-dropping

  • Response headers — the RLS can emit RateLimit-Limit / -Remaining / -Reset (a standardized set of HTTP response headers — an IETF draft — telling the client its ceiling, how many calls remain, and when the window resets) so clients can self-throttle instead of blindly retrying into a 429. It reports the closest-to-limit descriptor.
  • Quota mode — a set of descriptors that only trips the request when all of them are over, vs the default "any one trips it". Used for token/quota accounting semantics.
  • replaces — one descriptor's limit can supersede another's, so you can grant a user a higher limit on a single endpoint without inflating their category limit.
  • share_threshold — wildcard matches (files/*) can share one counter instead of one-per-value, controlling both fairness and key cardinality.
  • detailed_metric / value_to_metric — opt-in to per-value metric cardinality for debugging, explicitly gated because cardinality explosions are a real cost.
  • Unlimited / whitelisting — a descriptor can be marked unlimited (checked, never blocked) or simply carry no limit (effectively allow).

10 · A design question, worked end-to-end

Prompt
"Design rate limiting for a multi-tenant public API behind an Istio mesh. Free tier 1k/day, paid 1M/day, plus 50 rps burst protection per key, and protect a /export endpoint at 10/min for everyone."

1 · Clarify & scope

Confirm: identity = API key (from header/JWT). Multi-region? (drives one-Redis-per-region vs global). Accuracy vs latency priority per limit. Fail-open or closed per limit.

2 · Layered enforcement

  1. Tier 1 — local L7 token bucket on each Envoy for the 50 rps burst per key. In-process, sub-µs, survives Redis outage. Burst = token-bucket's natural model. Per-key via descriptor-based local limits.
  2. Tier 2 — global RLS for the daily quotas (1k / 1M) and the /export 10/min. These need fleet-wide accuracy, so they go to Redis.

3 · Descriptor / config design

domain: api
descriptors:
  - key: api_key            # daily quota, value-specific via tier lookup
    descriptors:
      - key: path
        value: /export       # the per-endpoint override
        rate_limit: { unit: minute, requests_per_unit: 10 }
      - key: tier
        value: paid
        rate_limit: { unit: day, requests_per_unit: 1000000 }
      - key: tier
        value: free
        rate_limit: { unit: day, requests_per_unit: 1000 }

Envoy sends both descriptors; the daily-quota one AND the /export one are checked — either being over ⇒ 429.

4 · Storage & scale

Redis Cluster, sharded by cache key (each key = tenant+window, independent, shards cleanly). Per-second Redis split off if burst limits move global. Expiry jitter on. One Redis per region; daily quotas are per-region budgets (or a small reconciliation job if truly global).

5 · Reliability

/export and quota limits: consider fail-closed (cost/abuse). Burst limit is local ⇒ always on. Ship all new limits in shadow mode, watch near-limit + would-block stats, then enforce. Return RateLimit-* headers so good clients back off.

6 · Edge cases to raise proactively

Boundary burst on daily fixed windows (acceptable for quotas; note it); hot key for the biggest paid tenant (local over-limit cache + monitor); clock skew (NTP); retries amplifying load (limiter must sit before retry budget, and 429s must be non-retriable or jittered).

11 · Rapid-fire Q&A

Token bucket vs leaky bucket — one sentence each?

Token bucket permits bursts up to the bucket size while capping the long-run average — good for APIs that tolerate spikes. Leaky bucket drains at a constant rate and smooths output completely — good for traffic shaping where the downstream needs a steady feed.

Why does the Envoy RLS use fixed-window and not sliding-window?

Because it collapses to a single atomic INCRBY plus EXPIRE — O(1) memory, natively supported by Redis/Memcached, and correct under concurrency without locks. Sliding-log needs per-request O(N) storage and trimming; sliding-counter needs two keys and extra math. At the RLS's throughput, the atomic-counter simplicity wins, and the boundary-burst weakness is mitigated by short units, jitter, and the local over-limit cache.

How does the cache key encode the time window?

The key appends (now / unitSeconds) * unitSeconds — the floored window start. When the clock crosses into the next window the key changes, the counter naturally starts at zero, and TTL garbage-collects the old key. No reset job, no stored window state.

Why cache only over-limit verdicts locally, never OK?

Caching OK would let each proxy skip the shared INCR and under-count, breaking global accuracy and letting excess through. Caching OVER can only reject traffic Redis already rejected — it's safe by construction and turns a hot blocked key from N round-trips into N local hits.

Local vs global — when do you reach for each?

Local when you need speed, zero dependencies, and coarse protection (burst caps, connection floods), or as an always-on backstop. Global when correctness across the fleet matters — per-tenant fairness, daily quotas, cost control. Best systems layer both.

What breaks if Redis goes down?

The RLS call fails; Envoy's failure_mode_deny decides fail-open (default, keep serving) or fail-closed (reject). This is precisely why a local limiter tier is valuable — it survives the outage and provides a protection floor. For abuse/cost limits, prefer fail-closed or a conservative local backstop.

How is the read-modify-write race avoided?

By using INCR's atomic return value as the decision instead of a separate GET-then-INCR. Redis serializes the increments, so concurrent proxies can't both read a stale count and both allow.

How do you roll out a new limit without paging yourself?

Shadow mode: run the whole pipeline (count, stats, cache) but always return OK. Watch the "would-have-blocked" and near-limit stats, tune the threshold, then flip to enforcing. Config hot-reloads atomically, so no redeploy.

L4 vs L7 limiting — what can each actually see?

L4 sees connections, IP:port, SNI, bytes — no HTTP. Good for coarse connection-rate protection. L7 sees the full request (path, method, headers, JWT/mTLS identity), enabling per-API, per-user, per-tenant policy. Per-API in the local path comes from route matching; in the global path from descriptors.

How would you scale past one Redis's throughput?

Cut round-trips (batch descriptors, local over-limit cache), shard across Redis Cluster (counters are independent so this is clean), then if still bound push to per-node local budgets with periodic async reconciliation — trading exactness for removing the per-request hop. Name the accuracy cost of the last step.

12 · One-page cheat sheet

Algorithms

  • Fixed window — 1 int, 2× burst, O(1). RLS uses this.
  • Sliding log — exact, O(N) mem, pricey.
  • Sliding counter — 2 ints, smoothed, edge/CDN.
  • Token bucket — bursts ≤ B, avg r. Envoy local.
  • Leaky bucket — smooths output, shaping.

Envoy modes

  • L4 local — network.local_ratelimit, conn token bucket.
  • L7 local — http.local_ratelimit, per-route bucket, no ext call.
  • L7 global — http.ratelimit → gRPC RLS → Redis.

RLS request path (this repo)

  • gRPC ShouldRateLimit(domain, descriptors)
  • GetLimit() walks descriptor tree (map lookups + wildcard)
  • local over-limit cache short-circuit
  • GenerateCacheKeys(): key + floored window
  • Redis pipeline INCRBY+EXPIRE (atomic)
  • any descriptor over ⇒ overall OVER_LIMIT ⇒ Envoy 429

Trade-off one-liners

  • Local = fast + independent, inaccurate across fleet.
  • Global = accurate, adds RTT + Redis dependency.
  • Fixed window = simple + atomic, boundary burst.
  • Cache over-limit only (safe); never cache OK.
  • Fail-open for stability, fail-closed for abuse.
  • Layer local (tier 1) + global (tier 2).

Distributed gotchas

  • RMW race → use INCR return value.
  • Clock skew → NTP + coarse units.
  • Hot key → can't shard one counter; local cache + monitor.
  • Expiry cliff → TTL jitter.
  • Retries amplify → limiter before retry budget.

Operability

  • Stateless RLS → scale horizontally.
  • Config: file-watch or xDS, atomic swap.
  • Stats: near_limit alert @ 80%.
  • Shadow mode before enforcing.
  • Return RateLimit-* headers.
